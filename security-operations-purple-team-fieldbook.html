Module 01 / Security operations / endpoint / identity

SOC alert investigation and escalation

Learning objective: Determine whether an alert deserves escalation without treating an alert as proof of compromise.

Operational scenario

Fictional enterprise security desk receives a high-priority alert about a service account. The account normally runs a nightly inventory task. Your role is analyst; you are authorized to review redacted synthetic records and make a recommendation, not to reset credentials.

Evidence packet

RecordObservationLimits
08:10:00Z Identitysvc-inventory authenticated successfully via approved service endpoint from LAB-OPS02This is a confirmed successful authentication in the supplied identity record, not proof of maliciousness.
08:11:04Z EndpointLAB-OPS02 spawned powershell.exe with Get-Service inventory argumentsA read-only admin query is compatible with legitimate inventory; ancestry, signing, and approved job scope matter.
08:12:22Z NetworkService host contacted 198.51.100.19:443, marked unknown in local asset recordUnrecognized destinations merit inventory review, but the documentation-only address does not establish exfiltration.
08:15:00Z TicketCHG-817 authorizes inventory from 08:00 to 08:30, names LAB-OPS02; destination list missingTicket is supportive context, not blanket authorization for every destination.

Commands / analyst worksheet

Windows (owned test VM; observation only):
Get-Date -Format o
Get-Process -Name powershell -ErrorAction SilentlyContinue | Select-Object Id,ProcessName,StartTime
Get-WinEvent -LogName System -MaxEvents 10 | Select-Object TimeCreated,Id,ProviderName

Synthetic-only for identity and network events: use the displayed records. Do not attempt to connect to 198.51.100.19.

Worked investigation method

Join on host, account, event time, and approved change. First verify the process and identity were expected. Then ask the change owner whether the destination is in the documented inventory pipeline. Preserve the original alert, record gaps, and propose escalation only if approval or context fails.

Trap to avoid: An alert severity is a prioritization hint, not a finding. A single approved timestamp also cannot establish that the network destination is authorized.

Independent professional exercise

Create a four-row event timeline. Name the strongest benign hypothesis and the strongest concerning hypothesis, plus the exact record that could distinguish them.

Evidence deliverable

An incident triage note with 'observed', 'unverified', 'decision', 'owner', and 'next check'.

Module 02 / Purple team / monitoring design

Detection engineering and false-positive analysis

Learning objective: Translate a security hypothesis into measurable telemetry and a testable detection-review plan.

Operational scenario

Fictional defender rule alerts whenever a Windows process inventory command is launched. Analysts are overwhelmed during approved patch windows. A purple-team lab must preserve unusual behavior while reducing irrelevant alerts.

Evidence packet

RecordObservationLimits
Rule definitionAlert if a process name equals powershell.exe and command line includes Get-ServiceThe pattern captures a broad command and does not incorporate actor, scope, or approved work.
Event sample100 alerts; 60 mapped to maintenance windows; 25 reviewed; 15 unknownTime-window correlation does not establish legitimate activity; unreviewed cases cannot be labeled false positives.
Reviewed outcomesAmong 25 reviewed: 20 authorized, 3 policy exceptions, 2 undeterminedOnly reviewed outcomes support a bounded precision/false-positive analysis, with undetermined excluded or reported separately.
Operational contextAdmin service checks occur daily; unauthorized execution remains a concernSimple blanket suppression would remove genuine detection utility.

Commands / analyst worksheet

Synthetic analysis (no live queries):
reviewed = 25
confirmed_authorized = 20
confirmed_exceptions = 3
undetermined = 2

Report each denominator explicitly; do not claim 80% of all 100 alerts are false positives from a reviewed subset unless the sampling method supports that inference.

Worked investigation method

Define a hypothesis such as 'unexpected service inventory from accounts or hosts outside authorized maintenance scope'. Request process parent, signer, account, host, ticket, time, and destination context. Test on benign and injected synthetic scenarios. Define a response guide that asks for verification rather than automatic blocking.

Trap to avoid: Avoid allowlisting all PowerShell or all maintenance activity. Authentication by a legitimate account does not prove every command it ran is authorized.

Independent professional exercise

Design a six-field detection record and two safe synthetic test cases: one approved maintenance action and one unauthorized lab persona using the same command. Explain why the outcomes should differ.

Evidence deliverable

A detection design brief with signal conditions, false-positive caveats, triage procedure, acceptance test, and rollback policy.

Module 03 / Networking / application security

DNS / HTTPS anomaly during change control

Learning objective: Distinguish resolver, route, TLS, and application failures before recommending a fix.

Operational scenario

An internal web training portal intermittently fails after a documented load-balancer change. Staff propose disabling TLS checks to 'make it work'. Your task is to identify which observations support safer remediation.

Evidence packet

RecordObservationLimits
13:00Z ChangeLB configuration rollout CHG-522 completedThe deployment is correlated with symptom onset but not independently proven causal.
13:04Z DNSportal.training.test resolves to expected lab load-balancer addressName resolution is working for the inspected client at this time.
13:05Z TCPTCP 443 connection to the resolved address succeedsTransport to that endpoint/port appears reachable; this doesn't validate server identity.
13:06Z TLSCertificate presented for legacy.training.test, not portal.training.testA hostname mismatch explains the TLS trust failure for the inspected session.

Commands / analyst worksheet

Owned/authorized lab only:
# Windows
Resolve-DnsName portal.training.test
Test-NetConnection portal.training.test -Port 443
# Linux
getent ahosts portal.training.test
curl -I --max-time 8 https://portal.training.test

Never add -k or --insecure to make a TLS error disappear as a supposed fix.

Worked investigation method

Correlate LB change ID with certificate inventory, server-name routing, chain validity, and expected hostname. Preserve the failing handshake result and request an owner-approved certificate or LB configuration correction. Retest with normal certificate checks after change and record service behavior.

Trap to avoid: TLS negotiation failure is not a generic 'network down' condition. Disabling certificate validation removes an important trust check.

Independent professional exercise

Create a five-layer table: IP, route, DNS, TCP, TLS, HTTP. Mark each 'observed pass', 'observed fail', or 'not established'. Do not record HTTP success because TLS failed.

Evidence deliverable

Change-review finding with exact cause hypothesis, alternate explanations, rollback plan, and verification conditions.

Module 04 / Digital forensics / documentation / incident management

Evidence integrity and reporting quality

Learning objective: Create an evidence package that preserves raw observations, separates inference from proof, and supports repeatable reviews.

Operational scenario

An incident team receives exported synthetic logs from different time zones and a filename called 'proof-of-hack.txt'. There is no confirmed security impact. Your assignment is to normalize, label, and protect the record before any conclusions.

Evidence packet

RecordObservationLimits
Windows system log2026-11-15T09:31:20-06:00 · lab service restartEquivalent UTC time is 15:31:20Z if offset shown is correct.
Linux journal2026-11-15T15:31:15Z · application timeoutFive seconds before the normalized Windows event; clocks may be skewed.
Operator note09:32 local · 'attacker restarted service'An unsupported assertion; note contains no actor attribution.
Data handlingFile manifest contains names but no recorded hashes or custody historyA manifest alone cannot prove content integrity or who handled the export.

Commands / analyst worksheet

Owned test files only; use local copies, no private exports:
# Windows PowerShell
Get-FileHash -Algorithm SHA256 -Path .\sample-log.txt
# Linux
sha256sum ./sample-log.txt

Hash the exact file bytes you intend to preserve. Record algorithm, value, file size, collection time and custodian; do not confuse a hash with proof of authenticity.

Worked investigation method

Retain originals read-only, make analysis copies, record timestamps with offsets, document source reliability and collection tool, and compare hashes before/after transfer when authorized. Convert times to UTC while retaining raw source strings. Identify uncertainty from clock drift and missing log coverage.

Trap to avoid: The filename and operator's interpretation are not evidence of an attacker. Matching hashes prove byte-level consistency between inspected versions, not that the original data was truthful.

Independent professional exercise

Draft an evidence manifest with source, raw time, normalized UTC time, capture method, hash status, chain-of-custody gap, and minimum next observation.

Evidence deliverable

An analyst evidence register and one-page finding that clearly labels confirmed facts, hypotheses, limitations, owners and retention policy.
