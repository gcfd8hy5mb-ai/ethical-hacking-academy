Independent Systems & Incident Fieldbook

Four extended guided investigations for your own Windows laptop, a local Linux VM, or a synthetic dataset. The objective is not memorizing commands: it is learning to distinguish observations, explanations, and defensible next actions.

Sequence: establish authorization → collect a baseline → interpret findings → test competing hypotheses → report the evidence. These workshops are practice resources, not an official exam or a substitute for real enterprise supervision.

Unit 01 · Windows administration and security

Diagnose an unfamiliar workstation without changing it

Scenario. An authorized employee reports that an application is slow after a scheduled update. Your task is to build a reliable, time-stamped baseline, not to guess that malware is responsible. Windows process CPU measurements and service states are often misunderstood. The CPU property in Get-Process is accumulated processor time, not a live percentage. A stopped service can be healthy if configured for manual or trigger start.

Read-only sequence (your own laptop or Windows test VM)

Get-Date -Format o
$env:COMPUTERNAME
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,LastBootUpTime
Get-Process | Sort-Object CPU -Descending | Select-Object -First 8 ProcessName,Id,CPU,WorkingSet
Get-Service | Where-Object Status -eq 'Stopped' | Select-Object -First 15 Name,DisplayName,StartType,Status
Get-WinEvent -LogName System -MaxEvents 12 | Select-Object TimeCreated,Id,ProviderName,LevelDisplayName,Message

These commands read system state; however, security logs and event messages can contain personal identifiers. Keep notes locally, redact usernames and host names before sharing them, and do not run administrative commands just to make a screenshot look complete. The final event query can show an access error on restricted accounts; record that limitation rather than bypassing policy.

How to interpret the output

ObservationWhat it supportsWhat it does not prove
Process with high CPU timeSubstantial cumulative CPU usage since startThat the process is currently overloading the machine
Service shows StoppedThat service is not presently runningThat it is malfunctioning or hostile
Event close to update timePotential chronological associationThat the update was the cause
No relevant events returnedNo matching events in the inspected retained sampleThat the event never happened

Reasoning drill. Record a process snapshot, wait a short interval, and record a second. Compare accumulated CPU time alongside task-manager live usage. Write two explanations for any discrepancy: for example, a long-running background process versus a brief burst of load. In your lab notes distinguish wall-clock time from uptime, and record whether your timestamps include time-zone offsets.

Recovery decision. Do not stop services, remove processes, change startup settings, or alter security policy in this exercise. Recommend a reversible next observation such as checking the application log, correlating the update window, or reproducing the slowdown under supervision.
Unit 02 · Linux operating systems

Explain identity, permissions, processes, and service health

Scenario. Your isolated Ubuntu VM can read a configuration file but an application cannot access its log directory. Before changing permissions, determine the effective user, path ownership, group membership, and expected service identity. A permission failure is a combination of path permissions, process identity, and possibly a mandatory access control mechanism; changing everything to world-writable hides the real cause and creates new risk.

Read-only commands (owned or authorized Linux VM)

date --iso-8601=seconds
hostname
id
pwd
ls -ld . /var/log
stat -c '%A %U %G %n' /var/log
ps -eo pid,user,comm,%cpu,%mem --sort=-%cpu | head -n 12
systemctl --failed --no-pager
ip -brief address
ip route

Outputs vary by distribution, permissions, and whether the VM uses systemd. On some environments systemctl is unavailable; explain the environment rather than treating that as evidence of compromise. Use id to identify both the primary and supplementary groups of the current user. ls -ld reports directory metadata, not its contents. stat provides more precise ownership information.

Worked permission interpretation

Suppose stat shows drwxr-x--- root adm /srv/app-logs. The owner can read, write, and traverse the directory; the group can read and traverse; other users have no access. A process running as appuser would need an appropriate group or explicitly configured access. Even if the final file is readable, missing execute permission on an ancestor directory can block traversal. An ACL or security policy may further restrict access.

Evidence task. Draw a path-access diagram for the process user, its groups, the parent directory, the target directory and the target file. Document which layer has been observed and which remains uncertain. Recommend a least-privilege fix in words only—do not issue broad chmod -R commands. In a disposable VM, any approved change should first include a snapshot and an explicit rollback plan.

Common error. CPU, memory, service status, and file permissions describe different questions. One alarming line from one command is rarely enough to establish the root cause.
Unit 03 · Networking and troubleshooting

Trace a connection failure from local configuration to service response

Scenario. A user cannot open an internal training website. The failure could be local addressing, a default route, name resolution, firewall policy, server availability, or the web application. Testing one layer at a time prevents the classic mistake of assuming that a failed ping proves a server is down; many networks intentionally filter ICMP.

Windows inspection

ipconfig /all
route print
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443

Linux inspection

ip -brief address
ip route
getent ahosts example.com
curl -I --max-time 10 https://example.com

Use a known, permitted test endpoint and avoid collecting another person's private network data. example.com is an illustrative public domain, not a promise that every laboratory network permits Internet access. If offline, use the synthetic decision record below without making external requests.

LayerSample observationNext interpretation
Addressing192.0.2.25/24, gateway 192.0.2.1Documentation-only addresses; check whether gateway is valid for this fictional subnet
RoutingDefault route through 192.0.2.1A configured route exists, not necessarily a working path
DNSLookup times outInvestigate resolver reachability or policy before blaming the site
TCP443 connects but HTTP returns 503Network transport may be functioning while the application is unavailable

Reasoning drill. Produce a diagnostic decision tree beginning with local address and route, then resolver tests, TCP connection tests, and finally application status. State how the tree changes when DNS fails but a previously validated IP address is reachable. State why bypassing certificate validation is not an acceptable general remedy for TLS failures.

Authorization. Read-only connectivity checks to your own systems or explicitly approved endpoints are in scope. Do not extend the workshop into scanning other networks or testing third-party services without permission.
Unit 04 · Security operations and incident response

Build a defensible incident timeline from incomplete evidence

Synthetic case. An employee reports an unexpected sign-in notification. At 09:05 UTC an identity provider records a failed sign-in from an unfamiliar location. At 09:07 UTC a successful sign-in is logged for the same account, but the device identifier is missing. At 09:08 UTC a mailbox forwarding rule appears in an audit event. At 09:11 UTC the employee confirms they did not create it. At 09:17 UTC the authorized response team begins containment. These are fabricated training records; never label the unfamiliar location alone as proof of attack.

Evidence versus inference

ItemDirect evidenceWorking hypothesis
09:05 failureAttempt failed according to identity logCould reflect typo, unauthorized probing, or another legitimate cause
09:07 successProvider logged successful authenticationPotential unauthorized access, subject to device and session review
09:08 forwarding ruleAudit event describes rule creationPossible persistence or exfiltration path
09:11 reportUser denies creating ruleRaises concern but still requires validation of audit context

Priorities. Follow approved incident procedures: validate records and time synchronization, preserve evidence, inform the responsible security team, isolate affected sessions or disable risky forwarding rules only with authorized approval, and document each action. Changing credentials may be appropriate, but its timing and consequences must be coordinated with the identity and response teams. Keep affected users and operational stakeholders informed according to the incident communication plan.

Red-team versus blue-team perspective

An authorized red-team assessment might attempt to demonstrate a weakness in authentication, session governance, or alerting under a signed scope and rules of engagement. The defender's task is to detect, contain, analyze impact, restore safe operation, and improve controls. The same event can support multiple hypotheses; describe what additional logs would discriminate between them instead of inventing attacker intent.

Independent analysis. Draft a timeline of the five events, identify two alternative benign explanations, document three missing pieces of evidence, propose a preservation-first response plan, and write a brief executive summary separating confirmed facts from suspicions. The goal is a proportionate decision with an audit trail, not an aggressive response.

Field reporting · all four units

Reusable evidence and reasoning template

Write one report per unit. Keep files on your laptop. This page intentionally does not transmit, store, grade, or modify Academy progress.

  1. Authorization and scope: system owner, allowed machine, allowed activities, and boundary.
  2. Objective and baseline: problem statement, UTC/local timestamp format, relevant initial conditions.
  3. Observations: exact command or synthetic source, redacted representative output, and why it matters.
  4. Alternative hypotheses: at least two plausible explanations including a benign possibility.
  5. Uncertainty: missing data, known limitations, possible time skew, permission restrictions.
  6. Next safe test: read-only or reversible action, expected outcomes, decision threshold.
  7. Communication and recovery: who authorizes changes, impact, and rollback plan.
  8. Reflection: what the evidence establishes and what you still cannot conclude.

Self-review: Does every conclusion cite an observation? Are live-system commands distinguished from sample output? Have you avoided turning an unverified hypothesis into a declaration? Is each recommendation proportionate and within scope? A strong report can conclude that more evidence is necessary.
