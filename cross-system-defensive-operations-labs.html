Cross-System Defensive Operations Labs

Combine Windows authentication events, Linux service inspection, network controls, and evidence handling. These original workshops are designed to teach what commands mean, what conclusions follow, what remains uncertain, and how to document an authorized investigation.

Scope: use the synthetic records or only systems you own or are explicitly authorized to inspect. Run read-only commands, not corrective actions. No live security assessment, network scanning, privilege changes, or external tools are necessary. The page does not run the listed commands.

WORKSHOP 01 / Windows / identity

Windows authentication evidence and log limitations

Case: A fictional user says they were locked out of LAB-WIN01 after several failed attempts. You have permission to inspect the local test VM. Your task is to reconstruct an accurate timeline without assuming which person entered the password.

Before you begin: Use your own Windows VM or read the fabricated records. Do not collect passwords or enable new audit settings on a real shared computer.

Exact read-only commands or synthetic records

Get-Date -Format o
whoami /user
Get-WinEvent -ListLog Security | Select-Object LogName,RecordCount,IsEnabled
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddDays(-1)} -MaxEvents 10 |
  Select-Object TimeCreated,Id,ProviderName,Message

Illustrative output (not a live test)

2026-11-15T11:18:40-06:00
Security log: enabled, 2456 records
11:10:20 local 4625 An account failed to log on
11:10:50 local 4625 An account failed to log on
11:11:14 local 4625 An account failed to log on

Concepts and interpretation

Event 4625 reflects a logged failed sign-in. It must be read with logon type, account fields, source information, machine context and the actual provider message. This command shows at most ten records, so it is not an exhaustive search. Some security events require administrator permission; a permission error must be documented, not bypassed.

Practical workflow

  1. Write the current timestamp and identify the VM, without exporting a real user identifier.
  2. Record which logs are enabled and the time range and maximum count used.
  3. Compare 4625 messages with the reported lockout time, accounting for locale, time zone and possible clock differences.
  4. Identify whether policy, log retention, remote authentication, or incomplete auditing could explain missing events.

Objective evidence check

Produce a timeline with three events, direct observations, and a list of evidence that would be needed to establish attribution. State explicitly that three failures do not prove a malicious actor.

Troubleshooting: If access is denied, use the synthetic data. If no results appear, check whether the VM produces and retains those events before drawing conclusions. Never change log audit policy without authorization.

Completion standard

A defensible account-access investigation that distinguishes failed attempts, lockout policy, and identity attribution.

WORKSHOP 02 / Linux / authentication

Linux account and service auditing in an isolated VM

Case: A training administrator reports that an SSH login did not work. Determine whether the service is present, listening, and recording authentication events before diagnosing identity or network failures.

Before you begin: Use a local Ubuntu VM that you own. An SSH server need not be installed; a missing service is an acceptable finding. Do not expose SSH to the Internet to finish this exercise.

Exact read-only commands or synthetic records

date --iso-8601=seconds
id
systemctl status ssh --no-pager
ss -ltn
journalctl -b -u ssh --no-pager -n 20

Illustrative output (not a live test)

ssh.service - OpenBSD Secure Shell server
Active: active (running)
LISTEN 0 128 127.0.0.1:22
Nov 15 17:19:00 lab sshd[3210]: Failed password for invalid user training

Concepts and interpretation

A running service can still listen only on loopback, which is not directly accessible from another VM. The ss -ltn command shows listening sockets but not necessarily which process owns them. Journal content may be absent or named under sshd on some distributions. Authentication logs can include personal data; only use your own test records.

Practical workflow

  1. Confirm the distribution's SSH service name before interpreting an unknown-unit response.
  2. Inspect active state and the listener address without enabling or restarting the service.
  3. Compare the journal's timestamps with the claimed failure window.
  4. Propose whether the next read-only check should be routing, interface addresses, service configuration, or authentication policy, and justify why.

Objective evidence check

Sketch the flow from client to interface to TCP listener to authentication check. For the sample 127.0.0.1 listener, explain why another VM cannot directly connect.

Troubleshooting: If systemctl reports no ssh unit, record 'not installed/unknown' rather than installing it. On non-systemd environments locate the existing logging facility. Use logs already accessible to your own account.

Completion standard

A four-layer diagnostic explanation backed by service state, listener binding, time, and journal records.

WORKSHOP 03 / Windows + Linux / network security

Read-only firewall, routing, and DNS comparison

Case: Two owned VMs are in a host-only virtual network. The Windows client can reach a lab host by IP but the application name does not resolve. A defender must separate routing, resolver configuration, transport, and policy.

Before you begin: Use host-only virtual networking or offline example data. Do not scan third-party networks. Windows and Linux command groups apply to their respective operating systems.

Exact read-only commands or synthetic records

# Windows PowerShell
Get-NetIPConfiguration
Get-NetRoute -AddressFamily IPv4 | Select-Object -First 12 DestinationPrefix,NextHop,InterfaceAlias
Get-NetFirewallProfile | Select-Object Name,Enabled,DefaultInboundAction,DefaultOutboundAction
Resolve-DnsName example.com

# Linux terminal
ip -brief address
ip route
resolvectl status
getent ahosts example.com

Illustrative output (not a live test)

Windows LAB-WIN01 192.0.2.20/24
Linux LAB-LNX01 192.0.2.40/24
Both report host-only adapter
DNS name example.com: no answer (offline lab)
Firewall profile Enabled=True
Service TCP reachability: NOT TESTED

Concepts and interpretation

An enabled firewall profile is not proof that a specific packet is blocked. Resolver output reflects the selected resolution path; an offline VM might intentionally have no DNS. Route tables indicate configured forwarding decisions, not validated reachability. The sample 192.0.2.0/24 addresses are documentation-only, not addresses to probe.

Practical workflow

  1. Confirm host-only mode in your hypervisor and record both interface/subnet configurations.
  2. Compare local routes. Identify whether each host has an on-link route for the other illustrative address.
  3. Inspect firewall profile state only; do not disable defenses to 'fix' a lab.
  4. Record the DNS test as 'not available by design' if the lab is offline. Do not infer an application failure from that fact.

Objective evidence check

Build a five-layer table: adapter, IP/subnet, route, resolver, and service connectivity. Distinguish observed from not tested; propose exactly one owner-approved next validation.

Troubleshooting: If resolvectl is unavailable, inspect /etc/resolv.conf while noting it may be a stub. If PowerShell network modules aren't available, use ipconfig /all and route print. Firewall policies differ across hypervisors.

Completion standard

A conservative network diagnostic report that makes no claim about untested transport or application behavior.

WORKSHOP 04 / Defensive response / reporting

End-to-end evidence preservation and incident handoff

Case: A fictional enterprise has a Windows failed-login alert at the same time a Linux application becomes unavailable. Reconstruct the incident, identify evidence gaps, and propose a reversible owner-approved investigation plan.

Before you begin: Use only this fabricated evidence or test data from your own lab. Do not ingest unrelated coworkers' logs, inspect unknown accounts, or publish raw authentication records.

Exact read-only commands or synthetic records

SYNTHETIC CASE RECORD
2026-11-15T17:00:00Z  Windows: 4625 failed sign-in
2026-11-15T11:00:04-06:00 Windows: scheduled maintenance begins
2026-11-15T17:01:10Z  Linux: app service active
2026-11-15T17:01:18Z  Linux: upstream DNS lookup failed
2026-11-15T17:02:00Z  Monitoring: app check returned 503

For an owned local sample file only:
Windows PowerShell: Get-FileHash -Algorithm SHA256 .\sample-log.txt
Linux: sha256sum ./sample-log.txt

Illustrative output (not a live test)

Normalized UTC order:
17:00:00Z Windows failed authentication
17:00:04Z scheduled maintenance begins
17:01:10Z Linux app service state = active
17:01:18Z upstream DNS lookup failed
17:02:00Z monitoring records HTTP 503
No verified causal link between sign-in event and outage.

Concepts and interpretation

Sequence alone does not establish that an authentication event caused an application outage. Hash comparison can verify that a copied file has identical bytes, not its authenticity or the truthfulness of events. Time normalization must preserve original timestamps and offsets. Incident responders need an explicit authority boundary for each action.

Practical workflow

  1. Convert the offset-aware Windows maintenance time to UTC and retain the original value.
  2. Separate the Windows authentication signal from Linux application failures; propose two competing causal explanations.
  3. Identify which missing artifacts could meaningfully discriminate between the explanations, such as resolver logs or deployment approval.
  4. Write a handoff with scope, observation, uncertainty, suspected impact, owner, safe next check and rollback/stop conditions.

Objective evidence check

Deliver a five-row UTC timeline, two plausible hypotheses, three gaps, and a plan that requires no destructive actions. Do not claim compromise or confirmed root cause.

Troubleshooting: If a file is missing, report it instead of recreating a fake original. Where clocks may drift, show the uncertainty interval rather than inventing precision.

Completion standard

An evidence-based professional handoff that distinguishes direct facts from hypotheses and contains verifiable next steps.
