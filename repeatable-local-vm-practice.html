LAB 01 / Windows host + Ubuntu VM

Verify an isolated Linux training VM

1. Safe setup

Use an existing Ubuntu VM in VirtualBox/VMware/Hyper-V or another locally installed VM solution. Choose NAT or host-only networking; avoid bridging to a workplace network. Record the VM name, version, RAM allocation, network mode and a pre-lab snapshot in your hypervisor UI. Don't make system changes just for this lesson.

2. Commands to run locally

hostnamectl
cat /etc/os-release
uname -r
id
ip -brief address
ip route

3. Illustrative output

Operating System: Ubuntu ...
Kernel: Linux ...
uid=1000(student) ...
lo     UNKNOWN 127.0.0.1/8
ens33  UP      10.0.2.15/24
default via 10.0.2.2 dev ens33

4. How to interpret

The distro and kernel version are separate identifiers. ip -brief address shows interface addresses and ip route shows how destinations are routed. Exact interface names and addresses depend on the hypervisor. NAT doesn't necessarily isolate all traffic; use host-only networking when no Internet is needed.

5. Objective completion check

Record OS release, kernel, current UID, one interface address, current route and isolation mode. Compare against hypervisor settings. These are measured observations, not automatic proof of complete isolation.

When it does not match: If hostnamectl says systemd unavailable, use cat /etc/os-release and uname -r. If ip is missing, check the VM's installed network utilities. If the interface is DOWN, check virtual adapter settings before changing guest network configuration.

6. Reset / cleanup

No guest changes required. Restore the pre-lab snapshot if you made a mistake while setting up the VM.

LAB 02 / Ubuntu VM

Measure disk blocks and inode capacity

1. Safe setup

Start the lab VM with a snapshot. Perform only read-only measurements; do not create a flood of test files to simulate exhaustion.

2. Commands to run locally

df -h /
df -i /
findmnt /
free -h
du -sh "$HOME" 2>/dev/null

3. Illustrative output

Filesystem Size Used Avail Use% Mounted on
/dev/vda2   25G  10G  14G  42% /
Filesystem Inodes IUsed IFree IUse% Mounted on
/dev/vda2     1.6M  200K  1.4M   13% /

4. How to interpret

df -h measures filesystem blocks; df -i measures inodes. du -sh estimates the size of the current user's home directory and may omit unreadable contents. Memory availability comes from free -h, a separate resource. Figures are examples, not target values.

5. Objective completion check

Record free blocks, free inodes, and the mounted filesystem. Explain why a file creation error might happen with plenty of bytes but no inodes.

When it does not match: Some filesystems report inode counts differently; explain the output. Avoid scanning / or other users' directories with du. If findmnt is absent, read /proc/mounts.

6. Reset / cleanup

Read-only task; no reset required.

LAB 03 / Ubuntu VM

Build a service evidence timeline

1. Safe setup

Use a VM with systemd. If the VM has no systemd, use existing system logs and mark the limitation. Do not restart any service.

2. Commands to run locally

date --iso-8601=seconds
systemctl --failed --no-pager
systemctl list-units --type=service --state=running --no-pager
journalctl -b -n 20 --no-pager

3. Illustrative output

2026-11-15T14:20:00-06:00
0 loaded units listed.
... ssh.service loaded active running ...
Nov 15 20:19:55 labhost systemd[1]: Started ...

4. How to interpret

A lack of failed units does not prove applications are healthy. A journal entry contains a time and reported event, not automatically its root cause. If ssh is absent, select any existing service rather than enabling one.

5. Objective completion check

Identify one service name, its state, one timestamped log record and at least two plausible interpretations; note boot scope and time-zone differences.

When it does not match: A container may lack systemd or persistent journals. Record this and use lab-provided synthetic evidence instead of changing init systems or privileges.

6. Reset / cleanup

No configuration changes.

LAB 04 / Your own Windows laptop, ordinary PowerShell

Repeat a Windows process baseline

1. Safe setup

Open PowerShell without Run as administrator. Observe your own machine only, and avoid posting unredacted usernames or device identifiers.

2. Commands to run locally

Get-Date -Format o
whoami
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,LastBootUpTime
Get-Process | Sort-Object CPU -Descending | Select-Object -First 5 ProcessName,Id,CPU
Start-Sleep -Seconds 15
Get-Process | Sort-Object CPU -Descending | Select-Object -First 5 ProcessName,Id,CPU

3. Illustrative output

ProcessName   Id   CPU
explorer      3472 82.34
...
After 15 seconds:
explorer      3472 82.51

4. How to interpret

The CPU field is cumulative process seconds. Comparing two snapshots requires the same PID. Top-five rankings can change between snapshots, so an absent process is not proof it stopped. Start-Sleep pauses the PowerShell session only.

5. Objective completion check

Record your start/end timestamps, at least one repeated PID and the difference in cumulative CPU time. Explain why the number alone cannot identify malware.

When it does not match: Some processes restrict attributes. If the terminal returns an access error, inspect accessible processes without elevation; if no PID repeats, take another limited snapshot.

6. Reset / cleanup

Read-only observation; no reset.

LAB 05 / Your own Windows laptop, ordinary PowerShell

Correlate Windows service and event records

1. Safe setup

Use a named service already present on your system. Spooler is an illustration; do not enable or restart it.

2. Commands to run locally

Get-Date -Format o
Get-Service -Name Spooler | Format-List Name,Status,StartType
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-2)} -MaxEvents 15 | Select-Object TimeCreated,ProviderName,Id,Message

3. Illustrative output

Name : Spooler
Status : Stopped
StartType : Manual

TimeCreated ... ProviderName ... Id ...

4. How to interpret

Stopped plus manual startup may be expected. A nearby event is not a proven cause. The event provider and full message provide essential context.

5. Objective completion check

Identify one observed service state and one relevant event with its timestamp. Write a conclusion limited to what those records directly support.

When it does not match: If Spooler doesn't exist, choose another service with Get-Service and inspect read-only. If no events match, expand the window only if permitted and note log retention.

6. Reset / cleanup

No changes are needed.

LAB 06 / Windows or Ubuntu VM; use only an approved destination

Validate DNS, routing, and HTTPS as separate layers

1. Safe setup

An offline VM is acceptable; if Internet access is disabled, interpret the provided example rather than altering firewall or network isolation. In a connected VM use a permitted test site such as example.com.

2. Commands to run locally

# Ubuntu VM
ip -brief address
ip route
getent ahosts example.com
curl -I --max-time 8 https://example.com

# Windows PowerShell alternatives
Get-NetIPConfiguration
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443

3. Illustrative output

DNS: example.com -> address(es)
TCP 443: reachable
HTTP/1.1 200 OK
OR: curl: (6) Could not resolve host

4. How to interpret

DNS resolution, route configuration, TCP reachability, TLS identity validation, and HTTP response are distinct layers. A successful TCP connection alone does not establish HTTPS trust. An offline isolated VM may fail by design.

5. Objective completion check

Make a five-row diagnostic table (IP, route, DNS, transport, application). For each layer write observed, not tested, or unavailable—not guessed.

When it does not match: If no route exists in host-only mode, that's expected for external domains. Do not use -k or disable certificate verification. Retain isolation if it is part of the lab's authorization.

6. Reset / cleanup

No persistent changes.
