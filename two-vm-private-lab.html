New · Private two-machine lab

Attacker workstation + training target VM

Practice real HTTP requests and identify an object-level authorization defect across two separate Linux virtual machines. The workstation sends a deliberately limited request to an intentionally vulnerable practice web application in another VM.

This is a local computer lab, not a cloud AttackBox. The website cannot start virtual machines, and the exercise must be launched on a computer capable of running two guests.

1. Build the isolated network

VM A · Investigator

Ubuntu Linux, private adapter on an Internal Network named AcademyLab.

IP: 10.40.0.20/24

Role: authorized client, evidence collection and challenge report.

VM B · Deliberately vulnerable target

Ubuntu Linux, private adapter on the same dedicated Internal Network.

IP: 10.40.0.80/24

Role: synthetic account web service on TCP port 8766.

Critical: use an isolated internal virtual switch—not bridged, shared LAN, port-forwarded, or Internet-accessible networking. Remove extra NAT adapters before running the exercise. No default gateway or DNS server is required. A host-only network is not equivalent to a strict internal network because it allows host communication.

For installation and OS updates only, you may temporarily enable NAT on each VM, download the official OS and scripts, and then turn NAT off before starting the target. Use snapshots after initial setup and verify network isolation.

Resource planning: two lightweight Linux VMs can often run with around 2 GB RAM per guest, plus host and hypervisor overhead, but requirements vary. Confirm your computer supports virtualization and has adequate RAM and storage. The user interface itself works on a phone; these real VMs do not.

2. Configure the guests

In your hypervisor, set both VMs to the same internal switch. In each Ubuntu guest, use ip -br link to identify the dedicated private interface (often enp0s3, but do not assume it). Configure the static addresses above through Ubuntu network settings. Leave gateway empty.

Investigator VM

ip -br addr
ip route
# Confirm dedicated lab NIC: 10.40.0.20/24
# No default route / bridged adapter

Target VM

ip -br addr
ip route
# Confirm dedicated lab NIC: 10.40.0.80/24
# No default route / bridged adapter

If your interface remains on a 192.168.x.x home network, or the target has a default route to your physical router, do not start the vulnerable service; correct the VM network first.

3. Get the real training programs

Download these files into the appropriate VMs using a temporary installation-only network. Avoid copying scripts from untrusted mirrors. Both programs use Python 3 standard-library functionality.

VM A: Investigator

two_vm_client.py — source

This client accepts only four predefined actions against 10.40.0.80:8766; it does not scan arbitrary networks.

VM B: Target

two_vm_target.py — source

The target refuses to bind unless the VM owns its documented private IP, and accepts training requests only from the investigator address.

4. Investigate the vulnerable training target

Start the target in VM B, with the internal network verified. It intentionally allows the fictional guest role to read a synthetic owner's private record.

python3 two_vm_target.py
# Target starts on 10.40.0.80:8766
# Use Ctrl+C to stop

In VM A, run the training client:

python3 two_vm_client.py health
python3 two_vm_client.py guest-public
python3 two_vm_client.py guest-private
python3 two_vm_client.py owner-private

Expected evidence: the guest obtains HTTP 200 for account 102, even though it belongs to the owner. The JSON contains the synthetic flag TRAIN{TWO_VM_OBJECT_AUTHZ}. Explain why receiving that data demonstrates an object-level authorization defect.

5. Patch and verify

In VM B, stop the service with Ctrl+C, then restart it in patched mode:

python3 two_vm_target.py --patched

Repeat the guest and owner requests from VM A. The guest requesting owner record 102 should receive HTTP 403, while the owner request should still receive HTTP 200. This is a synthetic role-selection exercise, not a real authentication system.

Optional local regression tests, run within a guest that has the scripts installed:

python3 -m unittest -v test_two_vm_lab

Open test source. Testing source code is committed, but the tests have not yet been executed on your computer.
