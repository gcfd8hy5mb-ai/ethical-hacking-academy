Three-room web security investigation

Investigate three intentionally vulnerable web application scenarios across two Ubuntu virtual machines, then restart the synthetic target with corrected access controls and record real HTTP results.

The browser page provides instructions and local self-reporting. The actual requests and objective evidence checks run with Python 3 inside your investigator VM. It does not create or remotely control any VMs.

Three independent security rooms

Room 1

Object ownership

Detect an object access check missing from a fictional account service. Explain why the wrong role receives another person's record.

Room 2

Restricted report export

Investigate why a viewer can fetch an internal audit report that should require auditor privileges.

Room 3

Debug information exposure

Identify internal diagnostic data visible to a guest and validate server-side access restrictions after remediation.

All people, data and flags are fictional. Role query parameters are training switches, not real authentication. These exercises demonstrate authorization concepts, not a production-ready login design.

1. Prepare the same two-machine isolated network

Use the same private virtual switch from the two-VM setup guide. Configure the investigator at 10.40.0.20/24 and the target at 10.40.0.80/24. Both guests must share only their internal training network, without NAT or bridged adapters when the vulnerable service runs.

Safety check: verify the VM network adapter assignments and ip route on both guests. There must be no default route into your home, work or public network. The new target listens only on the target VM's designated training address and accepts requests from the investigator's address. Network isolation must still be verified by the learner; these checks are not a substitute for a hypervisor security audit.

2. Download the two training scripts

Download the scripts from GitHub while setup networking is temporarily enabled, then disable any NAT adapters again before starting the exercise.

Target VM

three_room_target.py

Runs the three fictional vulnerable endpoints on TCP port 8767.

Investigator VM

three_room_client.py

Records the six HTTP tests per target mode and calculates a local practice score.

Validation tests

test_three_room_lab.py

Automated localhost tests for all three scenarios.

3. Gather vulnerable-mode evidence

In the target VM, run the target program with its default intentionally vulnerable mode:

python3 three_room_target.py
# Expected: target on 10.40.0.80:8767 in VULNERABLE mode

From the investigator VM, use the fixed-target client to collect real HTTP responses. It records unauthorized and authorized access attempts for each room.

python3 three_room_client.py status
python3 three_room_client.py capture --phase vulnerable

Examine the output file ~/academy-three-room-evidence.json. For the vulnerable room, the unauthorized request should return HTTP 200 with synthetic training data. Your report should explain what evidence supports the finding and which controls are missing.

4. Apply the patch and verify every room

On the target VM, stop the intentionally vulnerable server using Ctrl+C and restart in corrected mode:

python3 three_room_target.py --patched

From the investigator VM, repeat the same checks and calculate your score:

python3 three_room_client.py capture --phase patched
python3 three_room_client.py grade

Expected: unauthorized requests now produce HTTP 403. Each authorized role must still receive HTTP 200; a patch that denies everyone is not a satisfactory fix. The grader compares actual observed response codes and the scenario's synthetic records.

5. How scoring works

45 points

Vulnerable access observed: three findings, 15 points each.

45 points

Unauthorized access denied after patch: three verifications, 15 points each.

10 points

All legitimate role requests continue to succeed after patch.

The objective score comes from the investigator VM's recorded HTTP responses. These records are locally editable and do not provide cryptographic proof of real independent work. A human assessor must review your methodology, written interpretation and actual VM configuration.
