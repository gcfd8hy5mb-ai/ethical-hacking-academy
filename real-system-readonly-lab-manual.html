Windows & Linux Real-System Lab Manual

Train independently on your Windows laptop and an isolated Linux virtual machine. Every workshop includes the exact read-only command, what it returns, why it works, expected variations, safe troubleshooting, and what evidence to document. These are guided real-system instructions—not a browser shell.

Safety boundary: use only computers and VMs you own or are explicitly authorized to administer. These commands are observational; avoid changing firewall rules, services, account privileges, file permissions, or production configurations. Output may contain personal or private identifiers—redact them before sharing.

Some examples use fictional machine names or synthetic incident evidence. Real output will differ. You don't need to install paid services or upload logs to complete the exercises. Your Academy lesson completion and existing grades are unaffected by this page.

W01 / Windows PowerShell / Lab 1 of 8

Establish a trustworthy workstation baseline

Goal: Identify the OS, current user, boot time, IP configuration, and running processes on your own Windows computer without changing any settings.

Why the technique matters

A baseline is the comparison point for later incidents. Operating-system version, uptime, user context and network configuration affect how logs and permissions should be interpreted.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

Get-Date -Format o
whoami
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,LastBootUpTime
Get-Process | Sort-Object CPU -Descending | Select-Object -First 6 ProcessName,Id,CPU,WorkingSet
Get-NetIPConfiguration | Select-Object InterfaceAlias,IPv4Address,IPv4DefaultGateway

Illustrative output

2026-11-15T14:10:00.0000000-06:00
LAB-WIN01\student
Caption: Microsoft Windows 11 Pro
LastBootUpTime: 11/15/2026 8:45:00 AM
ProcessName  Id   CPU    WorkingSet
explorer     3400 64.2   234000000
...

Interpret the result

Get-Date -Format o outputs an offset-aware timestamp. whoami identifies the security context. LastBootUpTime allows uptime comparisons. The CPU property is cumulative processor time, not instantaneous CPU percentage. A system may return multiple IPv4 interfaces, including virtual adapters.

Independent evidence exercise

Record the OS version, boot time, local timezone offset, and one network interface. Repeat the process snapshot after 20–30 seconds to determine whether the same PID accumulated CPU time.

When results differ: If Get-NetIPConfiguration is unavailable, run ipconfig /all; if protected processes hide attributes, describe the access limitation rather than elevating. Avoid publishing MAC addresses, usernames or your public IP in screenshots.

Scope and safety: Read-only commands only; no service restarts or security policy changes.

W02 / Windows PowerShell / Lab 2 of 8

Connect service status to event evidence

Goal: Investigate why an owned Windows lab service appears stopped while distinguishing expected startup behavior from failure.

Why the technique matters

Service state is an observation, not a diagnosis. Events need provider names, timestamps, messages and change history; event IDs cannot alone establish cause.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

Get-Service -Name Spooler | Format-List Name,Status,StartType
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-6)} -MaxEvents 20 | Select-Object TimeCreated,ProviderName,Id,Message

Illustrative output

Name: Spooler
Status: Stopped
StartType: Manual

TimeCreated           ProviderName             Id
11/15/2026 1:02 PM    Service Control Manager  7036

Interpret the result

The Spooler example may legitimately be stopped. Event 7036 denotes a reported service transition, but the event message and surrounding timeline are necessary for interpretation. The query limits the time window and result count.

Independent evidence exercise

Produce a three-row evidence timeline and two explanations for the service's state. Identify the exact additional record you would need to distinguish the explanations.

When results differ: Get-WinEvent may report no matching events or access restrictions. Check event retention and query scope before concluding an event never occurred.

Scope and safety: Do not start a service to satisfy the exercise. Use synthetic records if your laptop lacks the example service.

W03 / Windows PowerShell / Lab 3 of 8

Reason about accounts and effective access

Goal: Inspect your own account's security group memberships and verify the path permissions for an approved test directory.

Why the technique matters

An application can fail to access a file when the account, group, file ACL, or ancestor directory permissions do not match the intended policy.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

whoami /user
whoami /groups
Get-Acl $env:TEMP | Format-List Owner,AccessToString
Get-Item $env:TEMP | Select-Object FullName,Attributes

Illustrative output

USER INFORMATION: LAB-WIN01\student
GROUP INFORMATION: BUILTIN\Users Enabled
Owner: LAB-WIN01\student
AccessToString: ...

Interpret the result

whoami /groups lists token group information, not every entitlement an organization might grant. Get-Acl describes a path's ACL; effective access also depends on identity, inheritance, deny entries, and process context. TEMP may be private to the current profile.

Independent evidence exercise

Draw the path owner, group memberships and relevant allow/deny entries. State whether you can infer another account's access from the limited record.

When results differ: If the ACL output is long, inspect only the necessary rows. Do not alter ACLs or copy sensitive usernames into Academy notes.

Scope and safety: Inspect only folders you own or have permission to administer.

L01 / Linux terminal / Lab 4 of 8

Check identity, permissions, and path traversal

Goal: Explain file access using UID/GID, group memberships, owner/group modes, and ancestor directory permissions in an isolated Linux VM.

Why the technique matters

Even a readable file can remain inaccessible if the process lacks execute permission on a parent directory. A full investigation examines the entire path.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

date --iso-8601=seconds
id
pwd
ls -ld "$HOME"
stat -c '%A %U %G %n' "$HOME"
namei -l "$HOME"

Illustrative output

uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
drwxr-x--- student student /home/student
f: /home/student
drwxr-xr-x root root /
drwxr-xr-x root root home
drwxr-x--- student student student

Interpret the result

r, w and x on a directory mean listing, modification of directory entries, and traversal respectively. Group membership influences which permission class applies. namei -l describes every path component, whereas ls -ld shows the directory itself.

Independent evidence exercise

Trace how a process running under your user can traverse /home/student and explain whether an unrelated non-group account could do the same.

When results differ: If namei is not installed, inspect individual parents with ls -ld. Do not install extra packages just to finish this lab if your VM is offline.

Scope and safety: Avoid recursive chmod/chown or granting world-writable permissions.

L02 / Linux terminal / Lab 5 of 8

Distinguish memory, disk blocks and inodes

Goal: Measure the storage state of an isolated Linux VM and reason about why creating a file might fail.

Why the technique matters

Disk capacity and inode allocation are distinct limits. An application can report 'No space left on device' even when ordinary free-space commands show available blocks.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

df -h /
df -i /
free -h
findmnt /
ps -eo pid,user,comm,%cpu,%mem --sort=-%cpu | head -n 12

Illustrative output

Filesystem  Size Used Avail Use% Mounted on
/dev/vda2    20G  9G   10G  47% /
Filesystem  Inodes IUsed IFree IUse% Mounted on
/dev/vda2    150K  149K  1K   99% /

Interpret the result

df -h reports block capacity; df -i reports inode capacity. free -h reports memory and swap. None alone establishes which process or directory is responsible for a failure. Filesystem type and mount options also matter.

Independent evidence exercise

Record available blocks and inodes, then explain which resource would become exhausted first in the sample. Describe how you would identify the responsible workload with authorized, bounded read-only inspection.

When results differ: Some filesystems report inode information differently. If findmnt is absent, inspect /proc/mounts rather than assuming a mount type.

Scope and safety: Do not delete files or modify quotas; take a VM snapshot before any future owner-approved cleanup.

L03 / Linux terminal / Lab 6 of 8

Build a service and journal timeline

Goal: Correlate service process state and recent application logs on a test Linux VM.

Why the technique matters

A running service may be unhealthy due to a dependency; a missing journal entry may reflect retention, logging configuration, or insufficient privilege.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

date --iso-8601=seconds
systemctl --failed --no-pager
systemctl is-active ssh
journalctl -b -n 25 --no-pager

Illustrative output

active
Nov 15 17:05:01 lab-host systemd[1]: Started OpenSSH server.
Nov 15 17:06:07 lab-host test-service[1100]: dependency lookup timed out

Interpret the result

The ssh service name is distribution-dependent and may be sshd, ssh, or unavailable. systemctl --failed lists units in failed state. journalctl -b limits the view to current boot and -n 25 limits output length.

Independent evidence exercise

Find one log entry's timestamp, unit, and claimed condition. Identify two hypotheses and propose a bounded next log query for the responsible unit.

When results differ: If your VM does not use systemd, identify its init and logging system; do not treat 'system not booted with systemd' as evidence of intrusion. If journal access is restricted, record that.

Scope and safety: No stopping, enabling, disabling or masking services.

N01 / Windows + Linux / Lab 7 of 8

Separate addressing, routing, DNS and TLS

Goal: Use existing network commands to diagnose failures layer by layer on your own lab environment.

Why the technique matters

A route, DNS record, TCP handshake and authenticated HTTPS request answer different questions. A good investigator does not jump directly from a failed hostname lookup to 'the server is compromised.'

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

# WINDOWS PowerShell — owned lab or approved endpoint
Get-NetIPConfiguration
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443

# LINUX — owned lab or approved endpoint
ip -brief address
ip route
getent ahosts example.com
curl -I --max-time 10 https://example.com

Illustrative output

DNS answer: addresses resolved
TcpTestSucceeded: True
HTTP/1.1 200 OK

# Alternative error example:
curl: (6) Could not resolve host

Interpret the result

Resolve-DnsName and getent test local name-resolution mechanisms. A TCP connection success confirms transport reachability to that service and port, not server identity or application authorization. An HTTP response follows DNS, route, TLS and server processing.

Independent evidence exercise

Explain what each command would support if successful, and what a failure could mean. Describe why a certificate mismatch cannot be 'fixed' by permanently disabling verification.

When results differ: Network-isolated VMs may be intentionally offline. Complete the scenario using the provided illustrative output instead of changing VM firewall settings or scanning external hosts.

Scope and safety: Use only owned lab services or explicitly approved endpoints. Avoid probing arbitrary hosts.

R01 / Incident response / Lab 8 of 8

Write a defensible multi-source evidence report

Goal: Combine a Windows event, Linux journal line and network observation into one time-normalized report with uncertainty and a reversible next step.

Why the technique matters

Investigations fail when log times are mixed, direct evidence is confused with inference, and suggested fixes are not tied to scope and validation.

Guided commands or case records

Run commands only in your own laptop/isolated VM, when relevant. Samples are illustrative and not live results.

SYNTHETIC CASE RECORDS (not commands)
Windows job: 2026-11-15T11:02:00-06:00 deploy success
Linux journal: 2026-11-15T17:03:10Z dependency timeout
DNS test: 2026-11-15T17:04:00Z lookup failed
Service check: 2026-11-15T17:05:00Z active

Illustrative output

Normalized timeline:
17:02:00Z Windows job reported success
17:03:10Z Linux app logged dependency timeout
17:04:00Z DNS lookup failed
17:05:00Z service was active

Interpret the result

Temporal order supports possible relationships, not a proven cause. A deployment job can succeed while a downstream dependency fails. A service can be active without serving requests. Include what was queried, relevant tool limitations and whether timestamps have known clock drift.

Independent evidence exercise

Produce a report with scope, four evidence rows, two competing causes, evidence gaps, a safe next check, the owner of any fix and a rollback/acceptance plan.

When results differ: If timestamps include ambiguous timezone abbreviations, retain the originals and seek system timezone configuration before ordering them. Do not guess the missing offset.

Scope and safety: No live incident containment or configuration changes are required for this exercise.

Evidence notebook · all eight labs

Professional troubleshooting record

Create a local text file outside the Academy to record your results. Do not upload unredacted command output. For every lab, document the machine label (not an actual public hostname), date and time with UTC offset, authorization, exact command, representative fields, your interpretation, alternative explanation, missing evidence and the next safe validation.

Closure rule: an exercise is complete when you can explain the evidence and its limits. No disruptive fix or proof of compromise is necessary.
