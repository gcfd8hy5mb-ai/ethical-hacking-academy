One workspace for real two-VM investigations

Use a single private browser workspace inside your investigator Ubuntu VM to capture evidence, document three security findings, compare patched responses, and submit an internally graded investigation.

This web page is a setup and study guide. The actual interactive workspace runs at 127.0.0.1:8770 inside your VM only—not on GitHub Pages, your phone, or the public internet.

Architecture and access limits

VM A · Investigator

Private IP: 10.40.0.20/24

Runs three_room_client.py and investigator_workspace.py.

Its browser opens http://127.0.0.1:8770 inside this same VM.

VM B · Practice target

Private IP: 10.40.0.80/24

Runs three_room_target.py on the isolated internal network, port 8767.

The target exposes synthetic vulnerable roles in training mode and protected roles in patched mode.

Do not expose the workspace or target: both guests must use a dedicated internal virtual switch, with no default gateway, NAT, bridged adapter, LAN access or port forwarding during training. VM host and hypervisor configuration must be reviewed separately; the Python services cannot guarantee isolation by themselves.

Install the scripts in the correct machines

Use a temporary setup network to obtain trusted source files from your GitHub repository. Disable that connection before running the vulnerable target.

Investigator VM files

three_room_client.py

investigator_workspace.py

Keep both files in the same folder.

Target VM file

three_room_target.py

Do not run it outside the isolated target VM.

Run the five-stage investigation

1. Validate the network and start the target

Check both VM interface addresses and routes. Then run on VM B:

ip -br addr
ip route
python3 three_room_target.py

2. Launch the private investigator workspace

Run on VM A from the folder containing its two scripts:

ip -br addr
ip route
python3 investigator_workspace.py

# Open inside VM A's browser:
# http://127.0.0.1:8770

Follow the workspace's sequence: scope confirmation, vulnerable evidence capture, written analysis of all three findings, patched retest, and final technical report.

3. Patch the target and compare responses

Only after your initial evidence and room analysis, stop the server on VM B with Ctrl+C, then run:

python3 three_room_target.py --patched

Back in VM A's workspace, select the patched capture button and compare HTTP 403 for unprivileged roles with HTTP 200 for authorized roles.

4. Complete the report and lock submission

The workspace requires a written analysis for each room and a remediation plan, each with at least 45 words. Its objective 100-point grade evaluates actual recorded HTTP responses but does not evaluate writing accuracy or prove that your network is isolated.

5. Shut down the training target

Stop both servers with Ctrl+C after the exercise and remove any temporary network access. Record what was tested and any unresolved issues.

Validation and pending work

Automated tests are included: workspace regression tests. Run them from the scripts folder:

python3 -m unittest -v test_investigator_workspace test_three_room_lab

This is a restricted browser-to-local-workspace connection, not a general remote shell, real login integration or one-click VM launcher. GitHub code and structural checks do not establish that the workflow works on your computer; VM acceptance and independent technical security review remain pending.
